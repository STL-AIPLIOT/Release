# BT 상대 30판 분석 + pursuit 거리 게이트 적용

- 작성일: 2026-08-04
- 표본: **30판** (60초 제한, ownship = `sac_mlp_obs8_iter400` / stil8, target = `AIP_STIL.dll`)
- 직전 보고서(`analysis/bt_remeasure/BT상대_재측정_보고서_20260804.md`)의 11판을 30판으로 확대한 것이다.
- 재현 명령은 §7.

## 0. 결론 세 줄

1. **60초 안에서는 패배가 드물다** — 30판 중 추락 1판, 지배적 결과는 **timeout 29판 / 양측 무피해**.
   문제는 지는 게 아니라 **교전이 성립하지 않는 것**이다.
   단, 이 "드물다"는 60초 조건의 산물이다. 대회는 200초이고 120초 학습에서는 추락률이 1.00 이다 (§6-1).
2. **못 쏘는 원인은 각도다.** 30/30판이 WEZ 사거리에 들어가지만, 밴드 안 `|ATA|` 중앙 60.2°,
   **30판 전체 최선이 15.39°** — 실제 게이트 1.0°의 15배다. 사거리는 문제가 아니었다.
3. **`pursuit` 거리 게이트를 넣었고, 짝이 되는 `closure` 항을 함께 넣었다.**
   게이트만 넣으면 4 km 밖이 무신호 구간이 되어 붙을 이유가 사라진다.

## 2. 왜 못 쏘는가 — 세 가설을 분리 측정

`tools/analyze_wez_window.py`(신규)로 호스트 `GeoMathUtil` + `_repair_degenerate_angle()` 을 써서
30판 전 프레임을 재계산했다. 판정식은 `update_damage()` 와 비트 단위로 같다
(`min_range <= D <= max_range` **and** `|ATA| <= angle_deg/2`, 각도 epsilon 없음).

| 가설 | 측정 | 결과 |
|---|---|---|
| (a) 밴드 체류가 너무 짧다 | 통과 60회, 체류 중앙 **1.34초**, 판당 밴드 내 159 프레임 | **아니다** |
| (b) 밴드 안에서 기수가 안 맞는다 | `\|ATA\|` 중앙 **60.2°**, 30판 전체 최선 **15.39°** (게이트 **1.0°**) | **이것이다** |
| (c) 최소 사거리보다 더 파고든다 | 152.4 m 미만 프레임 510건 | 부차적 |

**피해 조건 충족 프레임: 0 / 30판.**

체류 시간은 판당 2.7초로 충분하다. 문제는 그 2.7초 동안 기수가 최선 15° 어긋나 있다는 것이다.

> **`wez_entry_bonus` 상향은 무의미하다.** `my_reward.py` 의 진입 게이트는 호스트와 같은
> 엄격 반각(1.0°)이라, 이 30판에서 `wez_entry` 는 **한 번도 발화하지 않았다.**
> 발화하지 않는 항의 계수를 올려도 0 × 큰 수 = 0 이다. 직전 보고서 §5 의 이 처방은 철회한다.

## 3. 왜 붙지 않는가 — 보상이 이탈을 사줬다

30판 66,461 프레임의 거리·`|ATA|` 분포로, 게이트 이전 `pursuit` 이 어디서 나왔는지 센다.

| 거리 구간 | 프레임 | 비율 | \|ATA\| 중앙 | pursuit/step | 누적 |
|---|---:|---:|---:|---:|---:|
| 915 m ~ 2 km | 1,530 | 2.3% | 1.1° | +0.600 | 917.8 |
| 2 ~ 4 km | 7,042 | 10.6% | 0.7° | +0.597 | 4,204.5 |
| 4 ~ 8 km | 24,540 | 36.9% | 4.5° | +0.592 | 14,538.4 |
| **8 km 초과** | **33,349** | **50.2%** | 3.6° | +0.580 | **19,336.1** |

**누적 38,996.8 중 33,874.5(86.9%)가 4 km 밖에서 나왔다.**
8 km 밖에서 기수만 적 쪽으로 두면 `pursuit` 이 최대치(0.6)에 거의 붙는다.
붙어서 얻는 것(1.34초 × 0.6 = 0.8)보다 **멀리서 조준만 유지하는 것이 압도적으로 이득**이었다.

거리 중앙값이 8 km 에 고정된 것은 정책의 실패가 아니라 **보상 설계의 최적해**였다.

## 4. 적용한 변경 — `student/my_reward.py`

### 4-1. 각도 shaping 거리 게이트

```python
"angle_full_range_m": 914.4,   # 이 이내면 계수 1.0 (WEZ max_range_m)
"angle_zero_range_m": 4000.0,  # 이 이상이면 계수 0.0
```

`pursuit` / `position` 에 거리 계수를 곱한다. `full_range` 안은 1.0, `zero_range` 밖은 0.0,
그 사이는 **선형**이다. 하드 컷오프를 쓰지 않은 이유는 컷오프 밖에서 기울기가 0이라
붙을 이유를 만들지 못하기 때문이다.

같은 30판 궤적에 적용했을 때:

| | 게이트 전 | 게이트 후 |
|---|---:|---:|
| `pursuit` 누적 | 38,996.8 | **1,932.3** (5.0% 잔존) |
| 보상이 살아있는 프레임 | 66,461 (100%) | **8,572 (12.9%)** |

### 4-2. `closure` — 게이트가 만든 구멍을 메운다

게이트만 넣으면 **4 km 밖은 `step_penalty` 외에 아무 기울기가 없다.** 실측 중앙 교전거리가
8 km 인데 거기서 무신호면 행동이 미정의가 된다. 이탈을 막으려면 이탈 자체에 값을 매겨야 한다.

```python
"closure_weight": 0.5,
"closure_span_m": 1000.0,
# closure = w * clip((직전거리 - 현재거리) / span, -1, +1),  full_range 밖에서만
```

설계 근거:

- **거리 변화량**에 비례하므로 에피소드 합이 `(시작거리 − 끝거리)` 에만 의존한다.
  나갔다 들어오기를 반복해도 **합이 정확히 0** — farming 이 원리적으로 불가능하다.
  ("가까우면 매 step 지급" 형태를 쓰지 않은 이유다. 계약 검사에서 왕복 6 step 누적 = 0 을 직접 확인한다.)
- 멀어지면 그대로 음수 → **이탈에 값이 매겨진다.**
- 크기: 11 km → 914 m 완주 시 누적 약 +5.0. `wez_entry_bonus`(3.0)와 같은 자릿수라 진입 보너스를 압도하지 않는다.
- `full_range` 안쪽에서는 끈다. 그 안은 `pursuit`/`overclose` 담당이고, 켜두면
  최소 사거리 아래로 파고드는 것까지 보상해 `overclose` 와 정면으로 싸운다.
- 한 step 2,000 m 초과 변화는 reset 으로 보고 버린다(에너지 항과 같은 처리).

## 5-2. BT 상대 학습을 켜면서 드러난 제약 — 벤더 target DLL 을 못 쓴다

`target_mode: behavior_tree` 는 지금까지 학습에서 쓰인 적이 없다. 켜 보니 즉시 죽었다.

```
File "src/dogfight/ai/native_bt.py", line 125, in CreateBehaviorTree
OSError: [WinError -529697949]   # 0xe06d7363 = ctypes 경계를 넘어온 C++ 예외
```

**DLL 문제가 아니라 XML 문제다.** `init()` 이 `createTreeFromFile("./Rule.xml")` 로
파일명을 하드코딩하므로 Release 루트에는 `Rule.xml` 이 **하나만** 존재할 수 있는데,
지금 거기 있는 것은 팀 트리용(98요소)이다. 벤더 `AIP_BASE_target.dll` 은 그 노드들을
등록하지 않으므로 파싱에서 던진다.

| | |
|---|---|
| 벤더 상대(`AIP_BASE_target.dll`) | **사용 불가** (팀 `Rule.xml` 이 깔린 동안) |
| 팀 상대(`AIP_STIL.dll`) | **정상 동작** — 스모크 통과, iteration 비용 고정표적 대비 +8% |
| 벤더 원본 XML | `C:\AIP_LIB\Rule.xml` (1104 B, 2026-05-20) 에 보존됨 |

둘을 동시에 쓸 방법은 파일명 하드코딩을 고치지 않는 한 없다.
따라서 본실행은 **`AIP_STIL.dll` 상대**로 돌린다 — 30판 측정과 같은 상대라 비교도 일관된다.

## 6-2. 다음 병목 예측 — `cos(ATA)` 는 필요한 곳에서 평평하다 (설계만, 코드 미적용)

거리 게이트는 "붙는 문제"를 다룬다. 붙은 다음 "조준 문제"가 남고, 지금 보상은 그쪽에
거의 신호를 주지 못한다. 밴드 안(거리계수 1.0)에서 `pursuit = 0.6 * cos(ATA)` 의 기울기:

| ATA | pursuit | 1° 줄일 때 이득 |
|---:|---:|---:|
| 60° | 0.3000 | 0.00902 |
| 15° | 0.5796 | 0.00262 |
| 5° | 0.5977 | 0.00082 |
| 1° | 0.5999 | 0.00009 |

**15° → 1° 전체 이득이 0.0204**, 밴드 체류 13 step(1.34초, step_ratio=6) 전체로도 **0.265** 다.
정작 보상인 `wez_entry_bonus` 3.0 은 **1° 절벽 뒤**에 있다. 즉 유도 신호가 보상의 **8.8%** 뿐이다.

실측이 정확히 이 모양이다: 30판 밴드 내 최선이 15.39° 에서 멈췄다.
`cos` 은 0 근처에서 미분이 0 으로 가므로, **구조적으로 마지막 15°를 좁힐 수 없다.**

### 처방 (다음 실험용, 아직 넣지 않음)

밴드 **안에서만** 살아 있는 날카로운 정렬 항을 더한다. 예: 로렌츠형

```
align = align_weight / (1 + (ATA / align_scale)^2)      # min_range <= D <= max_range 일 때만
```

`align_scale = 5°` 면 15° → 0.10, 5° → 0.50, 1° → 0.96 으로 **1~15° 구간에 기울기가 몰린다.**
가우시안 대신 로렌츠를 쓰는 이유는 꼬리가 두꺼워 15° 밖에서도 기울기가 살아 있기 때문이다.

- 사거리 밴드로 **엄격히** 게이트한다(`update_damage()` 의 사거리 조건과 동일).
  거리 계수를 재사용하면 2 km 부근에서 정렬 farming 이 생긴다.
- `align_weight` 는 체류 13 step 누적이 `wez_entry_bonus`(3.0)와 같은 자릿수가 되게
  잡는다 → 0.25 안팎.

**적용 시점**: 지금 도는 실험이 끝난 뒤. 실행 중 `my_reward.py` 를 고치면
env runner 가 재시작될 때 모듈을 다시 읽어 **실행 중간에 보상이 바뀐다.**

**적용 조건**: 재측정에서 거리는 줄었는데 `frames_hit_total` 이 여전히 0 이면 이 처방이 답이다.
거리도 안 줄었다면 거리 게이트 쪽(`closure_weight`)이 먼저다.

## 6-1. 대회 규정 대비 어긋남 — 우선순위를 다시 매겨야 한다

학습 중 `crash_rate` 가 100 iter 내내 **1.00** 인데 30판 평가에서는 **1/30** 이었다.
모순처럼 보였지만 원인은 단순하다: **교전 시간이 다르다.** 규정을 읽으니 셋 다 다르다.

| | 값 | 출처 |
|---|---|---|
| 대회 라운드 | **최대 200초** | `Docs/competiton_rules.md` §5 |
| 학습 | 120초 | 실험 YAML `max_engage_time` |
| 30판 평가 | 60초 | `run_local_dogfight --max-engage-time 60` |

### 두 수치를 그대로 비교하면 안 된다

학습의 `crash_rate` 1.00 과 평가의 1/30 은 **탐색 설정이 다르다.**

| | 행동 | 시간 |
|---|---|---|
| 학습 롤아웃 | **확률적** (SAC 샘플링, `alpha` 아직 0.08) | 120초 |
| `run_local_dogfight` 평가 | **결정적** (`RLActionProvider(explore=False)`) | 60초 |

따라서 "학습에서 100% 추락하니 대회에서도 그렇다" 는 결론은 **내릴 수 없다.**
baseline(`sac_mlp_obs8_iter400`)도 400 iteration 내내 학습 `crash_rate` 가 1.00 이었지만,
그 정책을 결정적으로 평가한 30판에서는 1/30 이었다.


### 추가 실측 (2026-08-04, 두 실행 대조)

| | baseline `sac_mlp_obs8_iter400` | 현재 `..._rangegate_bt_v1` |
|---|---|---|
| alpha (처음 -> 끝) | 1.000 -> 0.0086 | 1.000 -> 0.0181 |
| `crash_rate` < 1.0 인 iter | **0 / 92** | **0 / 48** |
| 후반 최근접 중앙 | 364 m | 226 m |

**두 실행 다 에피소드가 집계된 모든 iteration 에서 추락률이 정확히 1.00 이다.**
alpha 가 0.01 대까지 내려가 거의 결정적인데도 그렇다. 그런데 baseline 의 번들을
**결정적으로**(`explore=False`) 평가한 30판에서는 1/30 이었다.

설명: 학습 롤아웃은 정책 분포에서 **샘플링**하고, 평가는 **평균 행동**을 쓴다.
alpha 가 작아도 정책의 표준편차는 0 이 아니다. 고도 관측 해상도가 3% 뿐인 상태(§6-5)에서는
그 샘플링 잡음이 지면 충돌과 회복을 가르기에 충분하다.

**따라서 학습 `crash_rate` 는 배치 성능의 진단 지표가 아니다.** 판정은 결정적 30판으로만 한다.

다만 이건 그 자체로 문제다. 매 에피소드 `crash_penalty` -150 이 들어오는데 그 사건은
**배치된 정책에서는 거의 일어나지 않는다.** 즉 학습 신호의 대부분이 배치와 무관한 사건에
쓰이고 있다. 완화 방향은 셋이다 — (a) 고도 관측 해상도 개선(§6-5, 진행 중),
(b) `crash_penalty` 하향, (c) 평가도 샘플링으로 맞추기. **(a)를 먼저 한다.**

### 그래도 남는 사실

- 학습 에피소드 길이 중앙이 **42.4초**(baseline) / **39.6초**(현재)다. 120초 상한에 한참 못 미친다.
  즉 timeout 이 아니라 **추락으로 조기 종료**되고 있다 — 탐색 노이즈만으로 40초 만에 지면에 닿는다.
- 결정적 정책의 추락률은 **60초까지만** 측정된 적이 있다. 200초에서는 **아무도 모른다.**

> **D-4(`altitude_weight` 상향 보류)를 철회한다.** 보류 근거였던 "1/30판" 은
> 60초·결정적 조건의 값이고, 대회 라운드는 200초다. 판단을 내리려면 **200초에서 재측정**해야 한다.
> 그래서 §6-3 에 200초 30판을 추가했다.

### 어긋남 2 — 대미지 판정이 시간에 따라 완화된다 (학습 환경은 고정)

| Phase | 시간 | LOS | 거리 | 계수 |
|---|---|---|---|---|
| 1 | 0~100 s | < 1° | 500~3000 ft | 1.0 |
| 2 | 100~150 s | < 2° | 500~3500 ft | 0.3 |
| 3 | 150~200 s | < 3° | 500~4000 ft | 0.1 |

학습 환경의 WEZ 는 `angle_deg: 2.0` 고정 → 반각 **1.0°**, 즉 **Phase 1 만** 모사한다.
`Docs/competiton_rules.md` §6 도 이 차이를 명시적으로 경고한다.

**그런데 30판 실측 최선이 15.39° 다.** Phase 3 의 3° 로 완화해도 **여전히 5배 부족**하다.
즉 각도 문제는 §6-2 에서 본 것보다 더 중심적이다 — 완화 규정이 구해주지 못한다.

### 어긋남 3 — 초기 고도가 한 자릿수 다르다

| | 고도 |
|---|---|
| 학습 (`config.py:74` `initial_scenario.altitude_m`) | **7,000 m** |
| 대회 초기 배치 (§5) | 약 **2000~3000 ft = 610~914 m** (정확한 수치 별도 공지) |
| 추락 판정 | 300 m 이하 |

대회는 추락 바닥에서 **300~600 m 위**에서 시작한다. 7,000 m 에서 배운 고도 감각은
그 구간에 적용되지 않는다. (규정 문서가 "정확한 수치는 별도 공지" 라고 하므로 확정값은 아니다.)

### 지금 도는 실험은 그대로 둔다

이 실험은 **보상 게이트의 효과**를 묻는 것이고, 그 질문은 위 셋과 독립이다.
비교 기준선(30판/60초)도 조건이 일치한다. 다만 **재측정은 두 벌 돌린다**:

- 60초 30판 — 구 30판과 직접 비교 (게이트 효과 판정)
- 200초 30판 — 대회 조건에서의 실제 추락률·교전 성립 여부

`run_bt_batch.ps1 -MaxEngageTime 200` 으로 같은 스크립트를 쓴다.

## 6-4. 실행 순서 — 이걸 틀리면 조용히 망가진다

**번들은 가중치만 저장한다.** 관측은 평가할 때 `student/my_observation.py` 를 그때그때
import 해서 만든다. 그래서 **학습 뒤에 관측 훅을 고치면 옛 가중치에 새 관측이 들어간다.**
`OBSERVATION_SIZE` 와 feature 이름이 그대로면 `check_observation_consistency.py` 도,
`metadata.json` 비교도 전부 통과한다 — **정규화 상수 하나만 바꾼 경우가 정확히 그렇다.**

대회 배치를 적용하려면 `ALT_MAX_M` 을 바꿔야 하므로(§6-5), 순서가 강제된다.

| 순서 | 작업 | 이유 |
|---|---|---|
| 1 | `sac_mlp_obs8_rangegate_bt_v1` 학습 종료 대기 | — |
| 2 | **그 번들을 먼저 평가** (60초·200초 30판) | 학습 시점 관측으로 평가해야 한다 |
| 3 | `my_observation.py` 의 `ALT_MAX_M` 수정 | 여기서부터 옛 번들은 평가 불가 |
| 4 | 계약 검사 재실행 → `stil_sac_mlp_obs8_match_v1` 스모크 | |
| 5 | match 본실행 (처음부터. 관측 스케일이 달라 checkpoint 재사용 불가) | |

**2와 3의 순서를 바꾸면 안 된다.** 되돌릴 방법은 훅을 학습 시점으로 되돌리는 것뿐이다.

### 자동 차단 장치

`train_rllib.py` 는 학습 시 훅 사본을 `artifacts/records/<name>/<tag>/my_observation.py` 로
남긴다. `tools/check_hook_drift.py` 가 그 사본과 현재 파일을 비교한다.
`run_bt_batch.ps1` 이 수집 전에 이걸 부르고, 드리프트면 **측정을 시작하지 않고 멈춘다**
(의도한 경우에만 `-AllowHookDrift`).

동작 확인: `ALT_MAX_M = 15000.0` -> `2300.0` 한 줄만 바꾼 사본으로 돌려 정확히 그 줄을
집어냈다(종료 코드 1). 같은 변경이 기존 일관성 검사는 전부 통과한다는 점이 요지다.

> 보상 훅(`my_reward.py`)은 records 에 저장되지 않아 같은 방식으로 검사할 수 없다.
> 보상은 행동을 만들지 않으므로 평가 정확도에는 영향이 없지만 **재현에는 영향이 있다.**

### 도구 사용 시 주의

- `run_local_dogfight` 로그는 **step_ratio=1 (60 Hz)** 이라 `--step-ratio 1` 을 줘야 한다.
  학습 로그(step_ratio=6)와 섞지 말 것.

  실제 최근접은 125.5 m 다. 거리 통계는 교전 로그(`replay_index.jsonl` / Tacview CSV)로 낼 것.
